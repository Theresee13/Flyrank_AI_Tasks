# Backend AI Engineering Retrospective

Over this internship track, I moved from building small API endpoints to connecting backend services with databases, background workflows, generated reports, and AI-assisted decision flows. The biggest change was learning to think about a project as an operational system rather than a collection of files that happens to run on my computer. A useful backend solution needs clear contracts, validation, reliable failure behavior, documentation, and evidence that its most important paths were actually tested.

The early API assignments gave me the foundation. In the FastAPI task API, I worked with CRUD endpoints, request models, status codes, and predictable error responses. I learned that validation is part of the public API contract: it is not enough for the happy path to create and update data. Invalid input, empty updates, and missing records also need responses that are clear and consistent. I carried that lesson forward into the other assignments, especially where a request triggers work that is not completed immediately.

The most valuable technical work for me was the background report service. The API creates a report request, but Inngest performs the slower work in durable steps. I learned to distinguish the initial HTTP response from the later workflow result, and to use an execution trace to understand what actually happened. The completed trace showed the requested eight-second step, while the intentional failure trace showed the failure step and error message. Seeing successful runs, failed runs, retries, and heartbeat jobs in the Inngest development dashboard made the workflow model much more concrete than reading documentation alone.

The PDF report assignment added another practical layer. I seeded a local dataset, aggregated it into a sales report, and rendered a real multi-page PDF with Playwright. It also introduced idempotency: sending the same request twice on the same day returns the existing report instead of creating unnecessary duplicates. A force option deliberately creates a new report when that is needed. This made me think about how APIs behave when a client retries because of a network problem. A duplicate request is not always a new business action, and the backend should express that distinction deliberately.

For the scraper assignment, I focused on responsible collection instead of simply maximizing the amount of data gathered. The project is restricted to Books to Scrape, a sandbox designed for practice. It checks the robots endpoint, identifies itself with a user agent, uses timeouts and a minimum delay, limits retries, caches raw HTML, validates normalized records, and records failures separately. I verified a run that retained 60 valid records, a cache rerun with no live content fetches, and an intentionally broken URL that produced a logged 404 without discarding the successful records. That assignment taught me that reliability and restraint are features, not optional polish.

I also learned that evidence matters. A README can describe an intended behavior, but a trace, a test result, an API response, or a real PDF makes the claim more trustworthy. During this work I improved the repository documentation so it records observed results instead of invented sample outcomes. I also learned to keep credentials out of commits and localize secrets in ignored environment files. One important habit I will keep is treating a secret exposed in chat or a screenshot as compromised and rotating it rather than assuming it is still safe.

There are still areas I would improve. I want to spend more time with automated integration tests that exercise complete API-to-worker-to-database paths. I also want to validate the Gemini-backed and visual workflow projects using my own replacement API key, then record real YES and NO branches in the interface. In a production version, I would add structured monitoring, stronger database migrations, and deployment checks rather than relying only on local development tooling.

The three transferable lessons I will take forward are: define behavior at the boundary, especially failures; make background work observable and idempotent; and document what was actually verified. I used AI as a collaborative coding assistant for code review, debugging, documentation structure, and test planning, but I reviewed the generated changes, ran the commands, and based this retrospective on the real repository work and local verification results.
